# Ether Tarot 全面重设计规格

## 1. 目标

将现有单文件 Three.js + MediaPipe 塔罗应用重构为可正式发布的现代 Web 应用。产品继续以手势抽牌为核心，提供完整的 78 张韦特体系单张抽牌体验，并为下一阶段基于用户问题的 AI 牌面解读预留稳定接口。

验收优先级依次为：

1. 手势稳定
2. 视觉惊艳
3. 加载速度

首个版本不接入真实 AI 服务，不实现多张牌阵，也不保存或上传用户问题。

## 2. 产品范围

### 2.1 本期包含

- 78 张韦特体系塔罗牌，无放回随机抽取
- 单张抽牌流程
- 手势作为主交互，鼠标与触屏作为等价降级方案
- 每张牌的中英文名称、正逆位牌义与分类解释
- 通用、爱情、事业、财运和个人成长五类解释，其中后四项为明确的主题分类
- 统一使用 `tarot_img/cover.jpg` 作为牌背
- 华丽占星与东方神秘融合的全新视觉
- 左下角本轮历史记录和左上角剩余牌数
- 面向未来服务端 AI 解读的接口和本地模拟实现
- GitHub Pages、Vercel 和通用静态服务器部署支持

### 2.2 本期不包含

- 真实 AI 模型或第三方解读 API
- 用户账号、云端历史或跨设备同步
- 三张牌及其他牌阵
- 支付、分享或社区功能
- 后端数据库

## 3. 技术架构

使用 Vite、TypeScript、Three.js 和 MediaPipe Tasks Vision。首个生产版本使用 Three.js `WebGLRenderer`，不以仍处于实验阶段的 `WebGPURenderer` 作为主渲染器。

建议模块边界如下：

```text
src/
├─ app/                 应用启动、生命周期和流程编排
├─ scene/               Three.js 场景、牌阵、卡牌、粒子和动画
├─ gestures/            摄像头、MediaPipe、滤波和手势事件
├─ draw/                单张抽牌状态机、牌堆和随机逻辑
├─ tarot/               78 张韦特牌结构化数据
├─ interpretation/      标准牌义查询、模拟 API 和 Provider 接口
├─ ui/                  界面组件、双语文案和无障碍状态
└─ styles/              视觉变量、布局和响应式样式
```

模块职责必须保持分离：

- 场景模块只负责展示和动画，不决定抽牌结果。
- 手势模块只输出稳定后的语义事件，不直接修改场景。
- 抽牌模块维护唯一的流程状态和牌堆数据。
- 牌义数据不包含 AI 生成内容。
- 解读 Provider 隔离本地标准牌义与未来服务端 AI 实现。
- UI 订阅应用状态，不自行复制抽牌规则。

## 4. 抽牌状态机

应用使用明确的有限状态机维护顺序：

```text
BOOT
→ READY
→ CAROUSEL
→ HOLDING
→ PLACED
→ CONFIRMING
→ REVEALING
→ READING
→ ARCHIVING
→ CAROUSEL
```

完成 78 张后进入 `COMPLETE`，仅在用户主动重置后恢复完整牌堆并开始新一轮。

状态语义：

- `READY`：资源可用，等待用户开始或授权摄像头。
- `CAROUSEL`：张开手掌后展示全部剩余牌的循环牌阵。
- `HOLDING`：稳定捏合后抓取一张牌背并允许移动。
- `PLACED`：松开捏合且卡牌处于揭示区域。
- `CONFIRMING`：在揭示区域稳定握拳约 0.5 秒。
- `REVEALING`：锁定结果、正逆位并播放翻牌动画。
- `READING`：中央保留正面牌和标准牌义供阅读。
- `ARCHIVING`：再次稳定张开手掌约 0.3 秒后执行粒子归档。
- `COMPLETE`：本轮 78 张已全部抽完。

任何动画锁定状态均忽略会造成重复转换的输入。

## 5. 手势与输入

### 5.1 手势映射

- 张开手掌：进入或继续循环牌阵；在阅读状态下稳定保持约 0.3 秒则归档当前牌。
- 拇指与食指捏合：连续识别规定帧数后抓取当前牌背。
- 保持捏合：移动抽出的牌。
- 松开捏合：揭示区域内则停放，区域外则回到牌阵。
- 握拳：仅在已停放状态有效，稳定保持约 0.5 秒后确认翻牌。
- 丢失手部：短暂保留当前状态；超过宽限期后安全释放卡牌，且绝不触发翻牌。

连续帧阈值和丢手宽限期在设备测试阶段校准，但必须通过统一配置管理，不得散落在业务代码中。

### 5.2 稳定策略

- 对指针坐标进行平滑滤波，降低卡牌移动抖动。
- 对捏合和握拳使用进入/退出不同阈值的滞回机制。
- 对离散手势使用连续帧确认和动作冷却。
- 摄像头推理与 Three.js 渲染循环解耦。
- 手势推理限制在适合设备的频率，3D 渲染继续跟随显示刷新率。
- 页面进入后台时暂停或显著降低推理频率。

### 5.3 降级输入

摄像头不可用、权限被拒绝或模型加载失败时，提供鼠标与触屏的等价流程。降级模式仍必须遵循同一状态机，不维护另一套抽牌规则。

## 6. 牌阵、随机与翻牌

### 6.1 循环牌阵

- 初始展示 78 张牌背组成的循环椭圆星轨。
- 每次归档后从可抽牌池移除该牌，下一轮依次展示 77、76 张，直至抽完。
- 所有牌背使用本地 `tarot_img/cover.jpg`。
- 当前可选牌使用鎏金轮廓、光晕或景深变化反馈悬停状态。

### 6.2 随机规则

- 采用无放回随机抽取。
- 抽中的牌和正逆位在握拳确认后、翻牌开始前一次性锁定。
- 正逆位独立随机决定。
- 逆位正面在翻牌完成后直接上下颠倒显示。
- 一轮内不得重复抽到同一张牌。

### 6.3 翻牌与归档

1. 握拳确认后锁定输入。
2. 确认目标正面纹理已加载。
3. 卡牌围绕竖直轴完成牌背至正面的 3D 翻转。
4. 展示正面、正位或逆位标记以及标准牌义。
5. 用户再次稳定张开手掌约 0.3 秒。
6. 当前牌从中央化为金色粒子并向左下角扩散、聚合。
7. 左下角历史记录新增真实牌面缩略图；逆位缩略图保持上下颠倒。
8. 剩余牌数减一，剩余牌重新展开为循环牌阵。

用户未执行归档手势前，结果牌必须保留在中央供阅读。启用系统“减少动态效果”时，粒子过程替换为短暂淡出和直接归档。

## 7. 牌义数据

每张牌采用统一结构：

```ts
interface TarotCard {
  id: string;
  number: number;
  arcana: 'major' | 'minor';
  suit?: 'wands' | 'cups' | 'swords' | 'pentacles';
  rank?: string;
  nameZh: string;
  nameEn: string;
  image: string;
  meanings: {
    upright: TarotMeaning;
    reversed: TarotMeaning;
  };
}

interface TarotMeaning {
  keywords: string[];
  general: string;
  love: string;
  career: string;
  wealth: string;
  growth: string;
}
```

数据要求：

- 覆盖 22 张大阿尔卡那与 56 张小阿尔卡那。
- 中文为主要阅读语言，英文用于牌名和必要术语辅助。
- 每张牌的正位与逆位均包含关键词、通用、爱情、事业、财运和个人成长解释。
- 构建或测试阶段校验 ID、名称、图片路径和全部牌义字段的唯一性及完整性。
- 本地标准牌义是稳定事实来源，不被未来 AI 输出覆盖。

## 8. 解读接口预留

本期提供统一 Provider：

```ts
interface InterpretationRequest {
  question?: string;
  cardId: string;
  orientation: 'upright' | 'reversed';
  topic: 'general' | 'love' | 'career' | 'wealth' | 'growth';
  locale: 'zh-CN';
}

interface InterpretationResponse {
  title: string;
  summary: string;
  guidance: string[];
  source: 'standard' | 'ai';
}

interface InterpretationProvider {
  interpret(request: InterpretationRequest): Promise<InterpretationResponse>;
}
```

本期使用 `LocalInterpretationProvider` 从标准牌义生成响应。下一阶段新增服务端实现：

```text
用户问题
+ cardId
+ 正逆位
+ 标准牌义
+ 主题与语言
→ Serverless Function
→ AI 模型
→ 结构化解读响应
```

API 密钥只存在于服务端环境变量，不进入浏览器构建产物。替换 Provider 不得要求修改抽牌状态机、牌库或 Three.js 场景。

## 9. 视觉与布局

### 9.1 风格

- 主风格：华丽占星。
- 辅助风格：东方神秘。
- 主色：深靛蓝、墨黑、古金和象牙白。
- 辅助元素：星盘、星轨、金线、克制的云纹、朱砂印记、方位刻度和留白。
- 避免无目的地堆叠传统符号或降低牌面可读性的装饰。

### 9.2 布局

- 中央：循环牌阵、揭示区域和当前结果牌。
- 左上角：剩余牌数和紧凑状态信息，格式类似 `余牌 77 / 78 · Remaining`。
- 左下角：本轮已归档牌的纵向历史记录。
- 右侧：桌面端牌义面板。
- 底部：移动端可展开牌义面板。
- 摄像头：弱化的小型半透明预览，可折叠。
- 手势反馈：当前动作、识别稳定度及确认进度环。

剩余牌数只在归档完成后更新。历史记录保存牌名、正逆位、真实牌面缩略图和抽取时间。页面刷新默认开始新一轮，本期不做永久存储。

### 9.3 响应式

- 桌面端使用完整 3D 椭圆牌阵和侧边牌义布局。
- 移动端使用适合触屏的横向可滚动或简化 3D 牌阵，不强行复制桌面构图。
- 所有主要操作必须可通过触屏完成。
- 尊重 `prefers-reduced-motion`，减少粒子、景深和大幅旋转。

## 10. 错误处理

- 摄像头拒绝、无设备或启动超时：解释原因并提供鼠标/触屏模式。
- MediaPipe 模型加载失败：允许重试，页面其余内容保持可用。
- 卡牌正面加载失败：保留牌背并提供重载，不归档错误结果。
- `cover.jpg` 加载失败：显示内置纯色牌背占位和明确错误。
- 手部短暂丢失：使用宽限期；超时安全释放卡牌。
- WebGL 不可用：展示简化二维抽牌体验。
- 所有核心运行资源本地化，不依赖外部牌背或占位图服务。

## 11. 性能

- 使用 Vite 产出带哈希的生产资源。
- 牌背优先加载，牌面按需预加载并使用有限并发。
- 根据设备性能限制像素比、粒子数量和后处理强度。
- 手势推理、资源加载和 3D 渲染互不阻塞。
- 不可见标签页暂停动画与摄像头推理。
- 场景对象、几何体、材质和纹理在移除时正确释放。

## 12. 测试与验收

### 12.1 数据测试

- 78 张牌数量准确且 ID 唯一。
- 22 张大阿尔卡那和 56 张小阿尔卡那分类准确。
- 所有图片路径存在。
- 正逆位及六个牌义字段全部存在且非空。

### 12.2 逻辑测试

- 78 次抽取无重复，第 79 次不可继续抽取。
- 重置后恢复完整牌堆。
- 结果与正逆位在确认后保持不变。
- 揭示区外松手回牌。
- 动画期间重复输入不产生额外抽取。
- 粒子归档结束后历史与剩余牌数同步更新。

### 12.3 手势测试

- 捏合、松开、握拳和重新张开手掌均需满足稳定条件。
- 握拳约 0.5 秒才确认。
- 阅读状态下张开手掌约 0.3 秒才归档。
- 手部丢失不会误确认或误归档。
- 坐标平滑不会造成明显延迟或漂移。

### 12.4 兼容测试

- 支持当前主流 Chrome、Edge、Firefox 和 Safari。
- 验证桌面摄像头、移动设备、鼠标、触屏和权限拒绝场景。
- 验证减少动态效果和低性能设备模式。
- 验证 GitHub Pages 子路径和 Vercel 根路径资源加载。

## 13. 构建与发布

- `vite build` 输出 `dist` 静态目录。
- GitHub Actions 自动构建并部署 GitHub Pages。
- Vercel 使用同一构建命令和静态产物。
- 摄像头功能仅在 HTTPS 或 `localhost` 环境启用。
- 本地开发、预览和生产构建使用明确的 npm 脚本。

## 14. 分阶段实施建议

1. 建立 Vite + TypeScript 项目骨架和测试基础。
2. 迁移并验证 78 张牌数据与图片资源。
3. 实现无放回抽牌状态机和本地牌义 Provider。
4. 迁移 MediaPipe Tasks Vision 并完成手势稳定层。
5. 重建 Three.js 循环牌阵、翻牌和粒子归档。
6. 完成华丽占星与东方神秘界面、双语内容和响应式布局。
7. 完成错误降级、性能优化和多设备测试。
8. 配置 GitHub Pages 与 Vercel 发布。

下一阶段接入真实 AI 时，仅新增服务端函数和远程 Provider，不改变本规格中的核心抽牌体验。
